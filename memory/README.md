# Machine memory: tool and template

The machine memory (`~/.config/ai-agents/`) is the shared memory of all local agents on a machine. This folder ships only the **tool** and an **empty template**, never the contents of an existing memory.

- `tools/memlint.py`: linter (structure, references, mem tags, secrets, agent entry points, backup coverage). The source is the live copy at `~/.config/ai-agents/tools/memlint.py`. `scripts/check-sync.sh` (runs before every publication) reports any drift.
- `template/`: `AGENTS.md` (general rules; since 2026-10-31 generated by `scripts/agents-template.py` from the sections of the live copy marked “allgemein” (general), without items marked “privat” (private); do not edit by hand, `scripts/check-sync.sh` checks that it is in sync), `AI_HANDOFF.md` (empty index), `entrypoints.conf` (agent entry points), `skills/` (skills shared by all agents, e.g. `loesungsqualitaet`; the source is `~/.config/ai-agents/skills/`, `scripts/check-sync.sh` checks that it is in sync).
- `tools/polaris-radar` (since 2026-11-01): Omarchy radar. Collects, without logging in, from GitHub and RSS what matters for customizations: updates and local changes of the installed git plugins, watched issues/repos, Omarchy commits and releases, newly listed plugins matching the keywords, and Omarchy news. Writes `handoff/omarchy-radar.md` (third-party text defused, in code font, marked as data). Runs after `omarchy update` via the hook `tools/polaris-radar.hook` (`~/.config/omarchy/hooks/post-update.d/`, in the background as the `systemd-run` unit `polaris-radar`, desktop notification on new hits) and on request. A run takes about 15 s and a few MB. Keywords and watched items live in `~/.config/polaris/radar.yaml` (template `tools/radar.example.yaml`); the names of installed plugins count as keywords automatically. X/Twitter cannot be queried (login, paid API).
  - **Security (since 2026-11-02):** section “Sicherheit” (security) in the radar and `~/.local/state/polaris/security.json` (health check line “Sicherheit”, yellow only). Checked are: installed packages (`pacman -Q`, `vercmp`) against the [Arch Security Tracker](https://security.archlinux.org) (only entries with an available fix; entries without a fix are counted, because many have not been maintained for years), the running kernel against kernel.org stable of the same branch (warning from `kernel_lag_warn` releases behind, default 4; also covers Omarchy's own kernels such as `linux-omarchy`), and actively exploited vulnerabilities from [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) of the last 30 days against the kernel and package names (those fixed according to the Arch tracker, and those probably fixed in a current kernel, are only mentioned). New findings trigger a desktop notification. If one of the three sources is unreachable, `security.json` records it as `error` and the health check line stays yellow (“check incomplete”) instead of showing “no findings”.
  - **Version matching (since 2026-11-04):** For KEV hits on a package, the radar fetches the affected version ranges (CPE, `versionStart*`/`versionEnd*`) from the [NVD](https://nvd.nist.gov) and compares them via `vercmp` with the installed version, without epoch and pkgrel. If it lies outside all ranges of the same vendor and product, the hit is only mentioned (“laut NVD nicht betroffen”, not affected according to NVD); if it lies inside, the warning names the range. Without version data (e.g. NVD status “Awaiting Analysis”) the warning stays. At most 5 NVD queries per run, responses cached for 3 days in `~/.local/state/polaris/nvd.json`. OpenSSH-style follow-up releases (`10.6p1`, Arch spelling `1.9.17.p2`) follow the CPE logic for the packages openssh, sudo and ntp (allow list; other packages keep plain `vercmp`, erring on the side of caution): upper bounds without `pN` compare only the base version (`<10.6` excludes `10.6p2`, `≤10.6` includes `10.6p1`), lower bounds without `pN` count the follow-up release as later (`>10.6` includes `10.6p1`), single entries with update field `p1` hit that release (and a package version without the suffix), unknown update fields (`rc1`, `sp1`, `ga`) count as affected; pacman's `vercmp` alone would read the letter as a pre-release (since 2026-11-09). Limitation: distribution backports without a new version number are not detected; the warning then stays (erring on the side of caution).
  - **Acknowledging assessed findings (since 2026-11-09):** a finding that has been checked and does not apply here (e.g. a KEV entry that only affects musl systems) can be acknowledged in `radar.yaml` under `security.acknowledged` with `id` (as in `security.json`, e.g. `kev:CVE-…`), `subject` (the installed state named in `security.json`, e.g. `openssh 10.6p1-2` or the kernel release), `until` (date, at most 90 days ahead) and `reason`. The acknowledgement only holds for exactly that finding and that installed state: after a package or kernel update, or after `until`, the finding is back. Acknowledged findings stay listed in the radar (“quittiert bis …”) and in `security.json` (`acknowledged`); the health check line turns green with “n quittiert”. Invalid entries are ignored and named; entries without a matching finding are reported as removable (not while a source was unreachable). The acknowledgement is also bound to the finding's text at the time it was first applied (`ack_basis` in `security.json`): if the assessment changes (NVD verdict, kernel lag, severity), the finding is open again until it is acknowledged anew with a different `until` (since 2026-11-10). Consequences: a kernel-lag finding ends its acknowledgement with every new upstream stable release (its text names the release); on the first run after this update the current text becomes the basis, so review existing acknowledgements once. Limitation: `security.json` itself is not protected by the guard hook; deleting `ack_basis` there rebinds acknowledgements to the current text (like `nvd.json` and the `POLARIS_RADAR_*` variables, an open point). Acknowledged ids are dropped from the radar's “seen” list, so a finding that returns triggers a new notification. Agents only acknowledge with the user's consent; with the guard hook active, writing `radar.yaml` asks first.
  - **Timer `polaris-radar.timer` (since 2026-11-02):** once a day (`RandomizedDelaySec=1h`, `Persistent=true`), about 3 MB download and a few seconds of CPU time, no long-running process; runs while the screen is locked too (no `polaris-awake` gate since 2026-11-08) and after resume first waits up to 2 minutes for the network (`nm-online`, since 2026-11-13). The hook after `omarchy update` starts the same unit. To turn off: `security: {enabled: false}` in `radar.yaml` or `systemctl --user disable --now polaris-radar.timer`.
- **Security tools (since 2026-11-05)**, against prompt injection and destruction. `install.sh` puts them into `~/.config/ai-agents/tools/` **but enables nothing**; that is the user's decision (agents must not change their own permissions). The source is the live copy, `scripts/check-sync.sh` checks that it is in sync.
  - `tools/claude-guard-hook.py`: hook for Claude Code. Logs every action (`~/.claude/guard/audit.jsonl`, 0600) and always asks before write operations in business systems via MCP connectors (send, create, modify …). Level `streng` (strict) additionally: once the session has read third-party content (web, mail/chat connectors, `~/Downloads`, `/tmp`, the Polaris project roots, `CLAUDE_GUARD_UNTRUSTED`), every action with side effects asks first (Bash, writes, MCP, WebFetch), however obfuscated. Changes to the protection itself (settings, hook, Polaris `config.yaml`, and since 2026-11-09 `radar.yaml`, whose `security.acknowledged` hides security findings) always ask. On errors the hook asks instead of letting the action through; if it does not start at all, `onFailure: block` blocks (Claude Code 2.1.295 or later). Limitation: obfuscated Bash commands bypass the text check at level `standard`; the fallback is snapshots and the log (which contains commands, 0600).
  - `tools/claude-guard-einschalten.sh [standard|streng|aus]`: adds the hook to or removes it from `~/.claude/settings.json` (timestamped backup, other entries stay; takes effect immediately, also in running sessions). `aus` = off. Recommendation: one week `standard`, then `streng`.
  - `tools/home-snapshots-einrichten.sh [--ausfuehren]`: hourly Btrfs snapshots of `/home` with snapper (root-owned, out of reach for agents; 12 hourly, 7 daily, 4 weekly). `~/.cache`, `~/.local/share/Steam` and `~/Games` first become separate subvolumes (reflink copy, then atomic swap; if anything fails, the original stays). Without the option it is a dry run; the real run only in a terminal window. `--ausfuehren` = execute. All root steps run in one call, so there is one password prompt; `--pkexec` uses pkexec (polkit dialog) instead of sudo, for machines whose rules require pkexec.
- `tests/`: tests for `memlint.py`, the radar and the mirror (`python3 -m unittest discover -s memory/tests`).

`install.sh` creates the memory from the template if `~/.config/ai-agents` does not exist yet. An existing memory is left untouched; only `tools/memlint.py` and the skills under `skills/` are updated, with the old versions backed up first; `memlint.py --link` links the skills to the configured agents. If omarchy-backup is set up, `install.sh` registers the memory there (`paths.d/ai-agents.conf`).
